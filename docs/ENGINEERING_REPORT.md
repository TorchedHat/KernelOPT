## Executive Summary

KernelOPT is a multi-agent GPU kernel optimization pipeline that takes PyTorch models, extracts the Triton kernels generated by `torch.compile`, and uses LLM-guided optimization to rewrite them for better performance. Prior to this sprint, the pipeline could not produce valid optimized candidates for multi-kernel PyTorch models — the correctness checker compared outputs at the wrong abstraction level, rejecting every candidate. **The pipeline now works end-to-end**: it synthesizes, optimizes, verifies correctness at both kernel and model level, re-stitches optimized kernels back into the compiled model, and reports honest speedup numbers. It also learns from every run and improves over time.

**Key results across KernelBench Level 1–3 problems:**

| Model | Kernel Speedup (NCU) | Correctness |
|-------|---------------------|-------------|
| MLP (bias+relu) | **1.48x** | 9/9 passed |
| MLP (wider) | **2.34x** | 6/6 passed |
| AlexNet-like (conv) | **1.38x** | 7/9 passed |
| LeNet-5 (multi-kernel) | **2.53x** (best kernel) | 4/6 kernels optimized |

> **Note:** These are single-kernel NCU latency speedups, not end-to-end model wall-clock speedups. For models where the Triton kernel is a small fraction of total compute (e.g., 6µs kernel in a 14ms model dominated by cuBLAS matmul), the model-level speedup is negligible. The pipeline now reports both: `Kernel: 1.46x | Model: 14.37ms → 14.42ms (1.00x)`. Full wall-clock benchmarks (eager vs compile vs optimized) are in progress.

## 1. Critical Fixes

### 1.1 Correctness Checker Level Mismatch (was: pipeline produced 0 valid candidates)

**Problem:** For synthesized PyTorch models (e.g., `ConvTranspose2d → relu → tanh`), the pipeline extracted a single Triton kernel for optimization but compared its output against the full compiled model. The full model takes model-level inputs (batch, channels, H, W) and produces model-level outputs; the single kernel takes kernel-level inputs (in_ptr0, out_ptr0, xnumel). Shape mismatch → `RuntimeError` → correctness "fails" → candidate rejected → 0 valid candidates → "no improvement."

**Fix:** Save the baseline standalone kernel during synthesis (`baseline_standalone.py`) and use it as the correctness reference. Both reference and optimized have the same `kernel_function(*get_inputs())` interface. Also fixed an in-place aliasing bug where both reference and optimized kernels wrote to the same tensor, causing broken kernels to falsely pass.

**Impact:** Pipeline went from 0% candidate acceptance to ~95% for correct optimizations.

### 1.2 Kernel Targeting (was: profiling wrong kernels)

**Problem:** The bottleneck selector could pick cuBLAS, cuDNN, or CUDA runtime kernels as the baseline target. These are vendor-optimized kernels the LLM cannot rewrite. This produced misleading speedup numbers (e.g., "594x") by comparing a Triton kernel's latency against an unrelated cuBLAS matmul's baseline.

**Fix:** Added explicit kernel classification (`triton`, `library`, `runtime`) and filtered to Triton-only targets for the synthesized pathway. Extended library patterns to cover `implicit_convolve_sgemm`, `xmma_fprop`, `nhwcAddPaddingKernel`, and other cuDNN/cuBLAS variants. Early exit with clear message when no Triton kernels exist.

**Impact:** Eliminates false speedup claims. Users see honest numbers.

## 2. Kernel Re-Stitching (New Capability)

### Problem
The pipeline optimized a single kernel in isolation but never verified whether the optimization was correct at the model level. A kernel that passes standalone correctness could still break the full model pipeline (wrong buffer sizes, corrupted intermediate tensors).

### Solution
After optimizing a kernel, swap the optimized `@triton.jit` body back into the full `synthesized_triton.py` (inside the `async_compile.triton()` block) and run the full compiled model to compare outputs against the unmodified version.

**Key engineering challenges solved:**
1. **Numel/shape constant mismatch** — The standalone kernel had different hardcoded tensor dimensions from the full model (different benchmark file). Solution: `_merge_kernel_body()` preserves original numels and shape constants while applying only optimization changes (eviction policies, block sizes).
2. **@triton.autotune incompatibility** — Raw `@triton.autotune` is incompatible with Inductor's `CachingAutotuner` `.run()` API. Solution: strip autotune decorator during re-stitching, extract best config (XBLOCK, num_warps, num_stages), and inject into the `@triton_heuristics.pointwise()` decorator's `size_hints` to bias Inductor's autotuner toward the executor's recommended block sizes.
3. **Kernel name verification** — The standalone kernel name could differ from the profiled target (stale benchmark files from prior compilations). Solution: strict name matching before re-stitch, graceful skip when names don't match.

**Validation:** Model-level correctness passes reliably on iteration 1 (5/6+ plans) with degradation in later iterations when autotune stripping introduces edge cases.

## 3. Search Tree with UCB Policy

### Motivation
From KernelEvolve and the Reliability Framework (arXiv 2603.29231v1): linear greedy search (always optimize from the single best candidate) misses better optima. A candidate at 0.95x might reach 1.5x after one more optimization step — but greedy discards it.

### Implementation
`SearchTree` maintains a tree of all kernel variants explored across iterations. Each node stores kernel source, profiled latency, speedup, and parent reference. Three selection policies:
- **Greedy** (default): pick the single best node — same behavior as before
- **Top-K**: pick the top-N nodes, enabling branching
- **UCB** (Upper Confidence Bound): balance exploitation (best speedup) vs exploration (least-visited branches)

Available via `--search-policy ucb` CLI flag. Tree persists to `search_tree.json` + `tree_kernels/` directory.

**Example tree output (L3 002, UCB, 2 iterations):**
```
[+] baseline — 10.1µs (1.00x)
  [+] autotune_xblock — 4.3µs (2.34x)
    [+] increase_xblock — 4.3µs (2.34x)
    [+] tune_eviction — 7.4µs (1.37x)
    [+] num_stages — 4.3µs (2.32x)
    [+] software_pipeline — 4.7µs (2.16x)
    [+] pin_xblock_2048 — 7.4µs (1.37x)
```

## 4. Memory Architecture — Design & Implementation

### 5.1 Research Context

KernelEvolve (Meta) uses a two-tier context memory architecture that was the primary inspiration:
- **Metadata store (relational DB):** Each explored kernel variant persists as `(id, parent_id, score, is_buggy, path_ref)` — lightweight, queryable via SQL/CTEs for graph traversal.
- **Object store (filesystem):** Kernel implementations, profiling results, and LLM-generated analysis reports stored on disk, loaded on demand.
- **Cross-session reuse:** When a new kernel arrives, the system queries historical kernels matched by operator type, input shapes, and hardware platform. If high-quality solutions exist, search starts from those instead of from scratch.

The Reliability Framework (Khanal et al.) warned that naive episodic memory hurts at long horizons — growing memory consumes context budget with diminishing returns. The recommendation: compress into structured insights, expire raw data after synthesis.

Anthropic's context engineering guidance reinforced: maintain lightweight identifiers and load data on demand (just-in-time retrieval), don't preload everything into the prompt.

### 5.2 Design Decisions

We considered three architectures:

1. **Full knowledge graph** — nodes (kernel patterns, strategies, hardware, profiling signals), edges (applied_to, improved, failed_on), community detection for automatic pattern discovery. Rejected as over-engineered for our current scale (~50 optimization attempts).

2. **Three-tier memory** — raw entries (ephemeral, per-run), synthesized patterns (durable, scored strategies per kernel type), and curated reference pairs (before/after kernel code). This was the right conceptual model.

3. **Simplified two-tier** — what we shipped. Strategy records per kernel type (success/failure counts, speedups) + reference pairs on disk. No graph, no community detection, no relational DB. The simplest thing that answers the question: *"what optimization should I try on THIS kernel?"*

### 5.3 What We Shipped: `OptimizationMemory`

**Location:** `kernelopt/kernelopt/knowledge_graph.py`

**Data model:**
```
pipeline_output/opt_memory/
├── strategies.json          # kernel_type → strategy_name → StrategyRecord
└── references/              # before/after kernel pairs (best per strategy)
    ├── pointwise__autotune_xblock_num_warps.json
    ├── fused_convolution__eviction_policy.json
    └── ...
```

**StrategyRecord** tracks per (kernel_type, strategy):
- `successes` / `failures` — absolute counts
- `total_speedup` — sum of speedups across attempts
- `best_speedup` — highest achieved
- `reference_id` — link to the best before/after pair

**Derived properties:**
- `success_rate = successes / (successes + failures)`
- `avg_speedup = total_speedup / attempts`
- `score = success_rate × avg_speedup` — used for ranking

**Kernel classification** (`classify_kernel()`): inspects kernel source for `tl.dot` → matmul, `tl.sum/tl.max/rblock` → reduction, `conv` → convolution, `fused_*` → named fusion, else → pointwise.

### 5.4 Integration Points

**Planner prompt injection** (`format_for_planner()`):
```
## Past Results (pointwise kernels)
1. autotune_xblock_num_warps — 100% success, avg 1.88x, best 2.26x (2 attempts)
2. vectorized_loads — 100% success, avg 1.49x
3. eviction_policy — 50% success, avg 1.05x
4. manual_unroll — AVOID (0% success, 3 attempts, avg 0.82x)
```

**Executor prompt injection** (`format_for_executor()`):
```
## Reference: pointwise kernel optimized 2.26x
Strategy: autotune_xblock_num_warps
Key change: Added autotune with XBLOCK 512-4096, num_warps 4-8

### Before:
[concrete kernel code with XBLOCK=128]

### After (2.26x faster):
[concrete kernel code with @triton.autotune configs]
```

**Recording** (in `profile_candidates()`): after each profiled candidate, calls `mem.record()` with kernel type, strategy name, speedup, correctness status, and before/after source. Only saves reference pairs for speedup > 1.1x. Deduplicates by keeping the best per (kernel_type, strategy).

**Fallback:** When no data exists for the current kernel type, aggregates across all types — "autotune_xblock worked on pointwise, might work on this fused kernel too."

### 5.5 Self-Improvement Lifecycle

```
Run 1 (new kernel type):  No memory → planner uses default strategies → 
                          records results → 3 references saved

Run 2 (same type):        Memory loaded → planner sees ranked strategies → 
                          avoids "manual_unroll" (0% success) → 
                          executor gets concrete example → better rewrites

Run N:                    Strategies converge → high-confidence rankings → 
                          new kernel types bootstrap from aggregate data
```

After 5+ runs across different models, the memory contained 21 reference pairs across 2 kernel types, with clear signal about which strategies to use and which to avoid.

### 5.6 Relationship to Search Tree

The search tree (`SearchTree`) and optimization memory (`OptimizationMemory`) serve different purposes:
- **Search tree**: within-run exploration — tracks all candidates in the current optimization campaign, enables backtracking and UCB exploration. Resets per run.
- **Optimization memory**: cross-run learning — tracks strategy success rates across all runs. Persists indefinitely. Feeds the planner and executor with ranked strategies and examples.

They complement each other: the search tree decides *which node to expand next*, the memory decides *which strategy to try*.

## 5. Code Generation Quality Improvements

### 5.1 Structured Iteration Log
The planner now receives a structured history of prior iterations: what was tried, what speedup it achieved, whether correctness passed. Prevents proposing the same strategy repeatedly.

### 5.2 Meltdown Detection
Inspired by the Reliability Framework: if the last 6 plans normalize to ≤2 unique strategies, a diversity boost is injected forcing the planner toward fundamentally different approaches (loop tiling, shared memory, algorithmic changes).

### 5.3 Partial Credit
When correctness fails, the failure description is included in the iteration log so the planner can salvage promising directions with different implementations.

### 5.4 Reduction Kernel Safety Constraints
Detects reduction kernels (max_pool2d, softmax, sum) and constrains the executor to safe-only changes: eviction_policy, num_warps, num_stages. Prevents the LLM from modifying tile sizes or loop bounds that break reduction semantics.

## 6. Multi-Kernel Optimization

### Capability
`kernelopt run model.py --multi-kernel` optimizes ALL Triton kernels in a compiled PyTorch model sequentially:
1. Synthesize the model via `torch.compile`
2. Identify all Triton kernels (e.g., LeNet-5 has 7)
3. For each kernel: build standalone → profile → plan → execute → verify → re-stitch
4. Output `final_model.py` with all optimized kernels

### Results on LeNet-5 (7 Triton kernels)

| Kernel | Type | Baseline | Best | Speedup | Re-stitched |
|--------|------|----------|------|---------|-------------|
| conv_relu_0 | pointwise | 94.9µs | 37.4µs | **2.53x** | Yes |
| conv_maxpool_1 | reduction | 27.0µs | — | 1.00x | No (correctness) |
| conv_maxpool_2 | transpose | 2.5µs | 2.4µs | **1.03x** | Yes |
| conv_maxpool_3 | reduction | 387.7µs | 366.8µs | **1.06x** | Yes |
| conv_maxpool_4 | reduction | 2.6µs | — | 1.00x | No (correctness) |
| addmm_relu_5 | pointwise | 4.8µs | 3.2µs | **1.51x** | Yes |
| addmm_relu_t_6 | template | — | — | skipped | — |

**4 of 6 pointwise kernels optimized and re-stitched.** Reduction kernels (max_pool2d fusions) remain challenging — the LLM-generated CPU reference for these complex fused kernels sometimes produces incorrect comparisons.

## 7. Honest Reporting

### End-to-End Model Timing
`time_model()` measures wall-clock GPU time of the full compiled model using `torch.cuda.Event` (warmup + measurement runs, median/min/max). Integrated after model correctness passes:

```
Kernel speedup: 1.46x (6.24µs → 4.26µs)
Model timing:   14.37ms → 14.42ms (1.00x)
```

This exposes the reality: when the Triton kernel is 0.04% of model time (the rest is cuBLAS matmul), optimizing it doesn't move the needle. Users see both numbers and can make informed decisions about where to invest optimization effort.
